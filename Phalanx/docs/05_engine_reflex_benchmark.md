# 05. Engine Reflex & Rule Latency Benchmark Report

본 문서는 `Phalanx.Engine`(C++20 네이티브 실시간 탐지/방어 엔진)의 핵심 컴포넌트인 **원자적 프로세스 동결(`ProcessActuator`)**, **인메모리 프로세스 트리 DAG(`ProcessTree`)**, 그리고 **로컬 결정론적 룰 엔진(`LocalRuleEngine`)**의 지연 시간 및 처리량을 실측 검증한 엔지니어링 벤치마크 보고서입니다.

## 2. 세부 벤치마크 데이터

### A. 로컬 룰 엔진 50,000회 연속 평가 벤치마크 (`EngineTests.exe`)

* **테스트 조건**:
  * 3종 대표 워크로드 균등 인입:
    1. 랜섬웨어 섀도 복사본 삭제 (`vssadmin.exe delete shadows /all /quiet` ➔ 즉각 사살)
    2. 오피스 파생 LOLBAS 스크립트 실행 (`winword.exe` ➔ `powershell.exe` ➔ 선제 동결)
    3. 일반 업무 소프트웨어 실행 (`notepad.exe readme.txt` ➔ 무간섭 패스)
  * 총 평가 횟수: **50,000 회** 연속 수행
* **실측 지표**:
  * 전체 소요 시간: `19.39 ms`
  * 최소 지연 (Min): `0.2 μs`
  * 평균 지연 (Avg): `0.354 μs` (354 ns)
  * 상위 95% 지연 (P95): `0.6 μs`
  * 상위 99% 지연 (P99): `0.7 μs`
  * 최대 지연 (Max): `51.2 μs`
  * 초당 처리량: `2,578,183` evals/sec

### B. 프로세스 트리 족보(Ancestry) 10,000회 역추적 벤치마크

* **테스트 조건**:
  * 인위적 4단계 계층 삽입: `explorer.exe(1000)` ➔ `winword.exe(1001)` ➔ `cmd.exe(1002)` ➔ `powershell.exe(1003)` ➔ `certutil.exe(1004)`.
  * `certutil.exe` 노드에서 최상위 조상까지 4단계 부모 체인을 탐색하는 `GetAncestry(1004, 5, false)` 함수를 10,000회 반복 호출.
* **실측 지표**:
  * 10,000회 누적 시간: `4.36 ms`
  * 평균 지연 시간: `0.43599 μs` (436 ns)

### C. 프로세스 동결 집행 방식 1:1 실측 (`SensorTests.exe`)

* **테스트 조건**:
  * 활성 스레드 4개를 보유한 타깃 프로세스를 대상으로 동결 집행 소요 시간 계측.
* **실측 지표**:
  * **1순위 `ntdll!NtSuspendProcess` (원자적 동결)**: `27 μs` (0.027 ms)
  * **2순위 `CreateToolhelp32Snapshot` + `SuspendThread` (스레드 순회 폴백)**: `31,600 μs` (31.6 ms)
  * **속도 격차**: `NtSuspendProcess`가 스레드 순회 폴백 대비 **약 1,170배 고속**.

## 3. 심층 기술 분석 (Deep Dive)

### A. 왜 룰 엔진 평가 지연이 354나노초(0.354μs)에 불과한가?
* **정규식(`std::regex`) 완전 배제**: 정규식 파서는 1회 매칭 시 50~200μs의 지연과 힙 동적 할당을 발생시킵니다.
* **비할당 경로 정규화**: 전체 경로에서 파일명 추출 시 `std::string_view` 기반의 포인터 오프셋 연산(O(1))만 수행합니다.
* **ASCII 대소문자 무시 고속 비교**: 영문 파일명 비교 시 힙 복사 없이 ASCII 비트 연산 기반의 바이트 비교를 수행하여 단 20ns 이내에 매칭을 완료합니다.

### B. 룰 엔진 연산 시간(0.354μs)과 네이티브 공격 윈도우(2ms)의 관계
본 벤치마크에서 계측된 `0.354 μs`는 **C++ 유저모드 CPU 상에서의 순수 룰 판정 알고리즘 연산 시간**입니다. 반면 기존 설계에서 언급된 `2 ms`는 **공격자가 첫 번째 악성 디스크 쓰기를 수행하기까지의 공격 윈도우(Attack Window)**를 의미합니다:

1. **스크립트 공격 윈도우 (PowerShell/WScript)**:
   * 프로세스 생성 ➔ .NET CLR 로드 ➔ JIT 컴파일 ➔ 스크립트 파싱 ➔ 페이로드 실행까지 **약 150 ~ 250 ms** 소요.
2. **C/C++ 네이티브 공격 윈도우 (컴파일된 랜섬웨어)**:
   * 프로세스 생성 ➔ PE 헤더 로드 ➔ IAT/DLL 매핑 ➔ `main()` 진입 ➔ 최초 디스크 쓰기까지 **약 0.5 ~ 2 ms** 소요.
3. **Phalanx E2E 차단 타임라인 (커널 오버헤드 포함)**:
   * 커널 프로세스 생성 및 ETW 버퍼링: `50 ~ 150 μs`
   * Phalanx 로컬 룰 엔진 판정: **`0.354 μs`**
   * Actuator 시스템 콜 (`OpenProcess` + `TerminateProcess`): `30 ~ 80 μs`
   * **전체 E2E 차단 시간 합산: 약 `0.1 ~ 0.25 ms` (100 ~ 250 μs)**.

결과적으로 Phalanx는 가장 빠른 C/C++ 네이티브 공격 윈도우(0.5~2ms)의 10% 미만 시점(0.15ms)에 프로세스를 물리적으로 사살할 수 있는 충분한 시간적 마진을 확보하고 있습니다.

## 4. 결론 및 향후 계획

* **Phase 2 검증 완료**: C++ 엔진 내부의 룰 판정 및 계층 탐색 알고리즘은 전체 파이프라인에서 측정 불가능할 수준(0.354μs)으로 병목이 전혀 없음을 입증했습니다.
* **Phase 2.5 연계**: 실제 디스크 쓰기를 즉시 시도하는 모의 네이티브 랜섬웨어(`MockNativeRansomware.exe`)를 대상으로, 커널 ETW 수집부터 시스템 콜 사살까지의 전체 E2E 파이프라인에서 카나리 파일 생성 누수(Leak)가 0%임을 실증하는 벤치마크를 수행할 예정입니다.
